# 决策 0053：安装包模式与本地 MCP 接入边界

**日期：** 2026-08-14  
**状态：** 已由项目负责人确认方向；尚未进入实现  
**关联方向：** 本地单用户 Web MVP、统一 LLM Gateway、Word/PDF/PPT 交付链  
**前置背景：** 用户已选择“方式三：安装包模式”作为未来对外接入方式。

## 1. 决策

项目未来采用**Windows 本地安装包 + 本地 MCP stdio bridge**作为首要分发路线：

```text
用户安装包
  -> 本地前端 + FastAPI 后端 + Worker + 受控 Python 运行时
  -> 受控项目工作区与交付物目录
  -> 本地 MCP stdio bridge
  -> 支持 MCP 的智能体宿主
```

用户仍需安装一次项目并配置自己的 DeepSeek API Key；智能体宿主只需要连接本地 MCP，不需要把项目源码、分析运行时和 Word 适配器重新下载到自己的沙箱中。

## 2. 为什么选择这个方向

- 保留当前本地单用户边界，不提前扩张为在线多用户 SaaS；
- 用户不需要理解 FastAPI、Worker、Python 依赖和 COM 调用细节；
- 可以复用现有 `server/`、`apps/web/`、受控 Python 执行环境、LLM Gateway 和 Word/PDF 渲染链；
- MCP 只承担“让智能体发现并调用项目能力”的协议适配，不复制项目业务语义；
- 本地工作区便于保留证据、执行记录、图表、DOCX/PDF/PPT 和审计信息。

## 3. 核心边界

### 3.1 MCP 不是业务 owner

MCP server 只能做工具发现、参数校验、调用现有服务、返回结构化状态和错误。以下语义仍由现有 owner 拥有：

- 实验要求与 L0-L3 判断：`server/app/modules/requirements/`；
- 项目与工作区：`server/app/modules/projects/`；
- 论文大纲、论文语义、内容充分性和交付关系：`server/app/modules/outlines/`；
- LLM 调用与供应商隔离：`server/app/modules/llm/`；
- 文档转换适配：`server/app/infrastructure/documents/`。

MCP 层禁止私造论文状态机、统计结论、权限结论、图表事实、路径规则和最终交付判断。

### 3.2 不提供一个无约束的“生成整篇论文”工具

对智能体暴露的能力应保持阶段化，例如：

1. 创建项目和录入实验要求；
2. 采集公开 URL 或导入用户提供的本地辅助文件；
3. 生成并确认证据卡片；
4. 检查数据集、生成分析方案并执行受控 Python；
5. 生成大纲和章节候选；
6. 运行内容充分性、证据追溯和解释边界校验；
7. 生成 DOCX/PDF/PPT，并返回交付物状态。

如果证据、方法或结果不足，MCP 必须返回结构化缺口，不得用模型文本填充成看似完整的论文。

### 3.3 文件、代码和密钥边界

- MCP 只能访问项目受控工作区，不接受任意宿主机绝对路径；
- 不开放任意文件读取、任意数据库 SQL、任意 shell 或 `shell=True`；
- Python 执行继续使用受控工作目录、依赖白名单、时间上限和输出上限；
- DeepSeek API Key 由用户在本地配置，不能打包进安装程序、日志、DOCX、PDF、PPT 或 manifest；
- 任何工具响应都应返回结构化状态、错误原因和可追溯任务标识，不直接暴露堆栈。

### 3.4 Word 和 PDF 的现实依赖

DOCX 生成可以随安装包提供。PDF 继续遵循当前合同：只由最终 DOCX 通过 DOCX→PDF 适配器导出，不维护第二套 PDF 排版。

Windows 上若没有可用的 Microsoft Word COM 环境，MCP 必须返回“DOCX 已生成、PDF 待转换”的明确状态，不能假装已经有 PDF，也不能偷偷启用第二套 PDF 正文布局。

## 4. 安装包的最小组成

- 前端构建产物；
- FastAPI 后端；
- 独立 Worker；
- 项目受控工作区初始化器；
- 受控 Python 运行时和依赖白名单；
- 本地 MCP stdio bridge；
- 启动器、健康检查和端口/进程生命周期管理；
- 本地配置向导（至少包含工作区位置、模型供应商配置状态和 Word 可用性检查）；
- 结构化日志和诊断导出，但不包含明文密钥。

## 5. 进入实现前必须新增的验收合同

安装包方向已确认，但这不是对本轮直接编码的授权。进入实现前需要单独编写并确认对应 SPEC，至少覆盖：

| 验收面 | 必须证明的结果 |
| --- | --- |
| 全新安装 | 在干净 Windows 环境启动前端、后端、Worker 和 MCP bridge。 |
| MCP 握手 | MCP-capable 宿主能够发现工具、读取 schema、调用成功并收到结构化错误。 |
| 工作区隔离 | 工具只能访问受控工作区，越界路径和任意命令被拒绝。 |
| LLM 配置 | DeepSeek Key 只经统一 LLM Gateway 使用，不写入产物或日志。 |
| 分阶段工作流 | 从要求、证据、数据、分析、大纲到交付物的状态可以被宿主观察和继续。 |
| 交付链 | DOCX 成功生成；Word 可用时 PDF 从最终 DOCX 导出；Word 不可用时返回待转换状态。 |
| 论文质量门禁 | 内容不足、证据不足、观察性结果越界时，工具返回缺口或边界，而不是生成伪完整论文。 |
| 升级与卸载 | 用户数据、配置和程序版本边界清楚，升级不覆盖用户工作区。 |

## 6. 非目标

- 本决策不把项目改成远程多租户平台；
- 本决策不把项目核心改写成某个智能体平台专属 Skill；
- 本决策不允许 MCP 绕过现有 API、owner、权限、证据和审计边界；
- 本决策不承诺所有智能体宿主都支持本地 stdio MCP；宿主兼容性必须作为安装说明和验收项明确；
- 本决策不改变当前“实验报告助手”而非“无证据论文代写器”的产品定位。

## 7. 主要风险

1. Windows 安装包需要处理进程启动、端口冲突、升级、卸载和杀毒软件误报；
2. Word COM 依赖必须在安装检查和用户提示中显式呈现；
3. MCP 工具一旦暴露任意路径或任意执行能力，会破坏当前项目的文件和安全边界；
4. 安装包只能改善接入体验，不能替代论文内容充分性和真实证据门禁；
5. 当前论文质量审查仍未收口，安装包实现应排在 P0 正文追溯清理和论文质量门禁之后。
